# Changelog

Notable changes, newest first. Entries accumulate under **Unreleased** and get
a version heading and date when a release is tagged.

Grouped as Added / Changed / Fixed / Removed, following
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow
[semantic versioning](https://semver.org/spec/v2.0.0.html), with the usual 0.x
caveat that minor releases may still break.

## 0.3.0 (2026-10-14)

### Added

- `unique_name` on `convex_deploy_key` and `convex_preview_deploy_key`: the
  key's full name as Convex lists it.
- Import accepts either the short name or the full listed name
  (`'playful-otter-123/github-actions (<uuid>)'`). The full name is matched
  exactly first, so a legacy unsuffixed key can be imported beside suffixed
  siblings. `name` is recorded as the short name, so configurations using it
  plan no replacement.

### Fixed

- `convex_deploy_key` and `convex_preview_deploy_key` work again now that
  Convex makes deploy key names unique by appending ` (<uuid>)`: a key created
  as `github-actions` is listed as `github-actions (cbd71ace-...)`. 0.2.0 looked
  keys up by exact name, so every create failed with "Error reading back
  created deploy key", saved state with a null `id`, the next refresh dropped
  it as deleted, and each apply made one more key. Now:
  - Create lists the keys before and after the create call and takes the one
    new key whose name matches. Creates against one deployment or project are
    serialised within the provider, so same-named keys created in parallel
    each find their own. If the key still cannot be identified, the secret is
    saved to state and the apply reports the error.
  - Read finds the key by its stable `id`. A key with no `id` in state (an
    import, or state written by 0.2.0) is adopted by `unique_name`, else by
    name when exactly one key matches. If none or several match, a key whose
    secret is in state is kept with a warning; one without a secret is
    dropped when missing, and fails with the candidates' ids when ambiguous.
  - Delete uses the key's full listed name, falling back to the secret only
    for a key that cannot be found in the list. A deployment or project that
    no longer exists counts as already deleted.
  - Listing keys is retried on transient failures.
  - `name` keeps the configured value, so there is no perpetual diff. A listed
    name matches the configured one when it is equal or is
    `<configured> (<uuid>)`; `ci` matches neither `ci-other (<uuid>)` nor
    `ci (old)`.

  Keys orphaned by 0.2.0 still exist in Convex and are not deleted by this
  fix; delete the extras in the dashboard.

## 0.2.0 (2026-08-03)

### Added

- `convex_log_stream` — streams a deployment's log events to Axiom, Datadog,
  a webhook, Sentry, or PostHog (logs or error tracking). One nested block per
  sink, exactly one required; switching sinks replaces the stream. Requires a
  Convex Pro plan. Credentials are never returned by the API, so they are kept
  from configuration; the webhook sink's `hmac_secret` is generated by Convex
  and stored in state.
- `convex_environment_variable` — sets an environment variable on a **running**
  deployment, through the
  [Deployment Platform API](https://docs.convex.dev/deployment-platform-api).
  This is distinct from `convex_default_environment_variable`, which only seeds
  deployments created afterwards and has no effect on existing ones. Takes a
  `deployment_url`, since regional deployments cannot be addressed by name.

### Fixed

- Idempotent writes on the Deployment Platform API are retried on transient
  failures. Convex is transactional, so applying several environment variables
  of one deployment in parallel could fail with a 503
  `OptimisticConcurrencyControlFailure`; this is now retried rather than
  surfaced. Log stream updates and deletes are covered too. Creates are
  deliberately excluded, since a failed create does not prove nothing was made.

### Changed

- Retry handling shared by both clients moved to `internal/apierr`.
- The provider now wraps two Convex APIs. `internal/convex` covers the
  management API; the new `internal/deployapi` covers the Deployment Platform
  API, which is addressed at each deployment's own URL and takes a `Convex `
  authorization prefix instead of `Bearer `. The same team access token
  authenticates both, so provider configuration is unchanged.
- Error decoding shared by both clients moved to `internal/apierr`.
  `convex.APIError` remains as a type alias.
- `api/openapi.json` renamed to `api/management-openapi.json` now that a second
  spec is vendored. `make fetch-spec` refreshes both; the deployment spec comes
  from the convex-backend repository, which is the only place it is published.
- CI actions updated to their latest major versions.

## 0.1.0 (2026-08-03)

Initial release.

### Features

- **Resources:** `convex_project`, `convex_deployment`, `convex_deploy_key`,
  `convex_preview_deploy_key`, `convex_custom_domain`,
  `convex_default_environment_variable`.
- **Data sources:** `convex_project` (by ID, or by slug within a team) and
  `convex_deployment` (by name, or by project plus a selector).
- Authentication with a team access token, personal access token or OAuth
  token, via the `token` attribute or `CONVEX_ACCESS_TOKEN`.
- Every resource supports import.

### Known limitations

- Deploy key secrets are returned by Convex only at creation, so they are
  stored in Terraform state in plain text and cannot be recovered by import.
- Default environment variables apply only to deployments created afterwards;
  Convex does not sync them to existing deployments.
- Custom domain verification is asynchronous, so `verified` is `false` until a
  later refresh picks up the DNS check.
- No acceptance test suite yet, so resource behaviour is verified by unit tests
  and an offline plan rather than against a live API.
